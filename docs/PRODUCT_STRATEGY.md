# Product Strategy — 從網路工具箱走向變更驗證器

## 一句話定位

Android Network Diag 不是另一套 ping、測速與 traceroute 集合，而是一個本機優先的「網路變更驗證器」：它記住問題發生前後的證據，指出哪一層改變，並驗證使用者採取的動作是否真的改善連線。

## 使用者真正遇到的問題

一般工具擅長回答「現在通不通」，卻很少回答：

1. 剛剛還能用，現在究竟改變了什麼？
2. 問題來自 Wi-Fi、電信商、DNS、VPN／加速器、IPv6，還是特定服務路徑？
3. 關閉加速器、切換 DNS、重連 Wi-Fi 後，是否真的改善，而不是剛好恢復？
4. 如何把足夠但不過度暴露隱私的證據交給客服、網管或朋友？

產品主流程應從「開一個工具、看一個數字」改為：

```text
描述症狀 → 建立基準快照 → 執行一個安全變更 → 自動重測 → 顯示差異與可信度 → 保留或復原
```

## 差異化支柱

### 1. Change Lab：可驗證的前後對照

這是最高優先、也是核心首頁體驗。

- 建立變更前快照：活動網路、底層傳輸、VPN／加速器狀態、DNS、公開 IP、IPv4/IPv6、Android 驗證狀態、關鍵 probe 與 Fastly 解析結果。
- 使用者選擇動作：切 DNS、關閉外部隧道後重測、重連 Wi-Fi、改用行動網路，或只加一則註記。
- 監聽 `NetworkCallback`，待網路穩定後自動重測，不要求使用者猜等待時間。
- 結果只突出有意義的差異，例如「HTTPS 恢復，但 DNS 沒變」或「底層仍是 Wi-Fi，關閉加速器後本地閘道恢復」。
- 對 App 自己可控制的 DNS 提供保留／復原；系統設定只提供 deep link，不假裝能代替使用者修改。

驗收條件：一次操作可產生 before/after 結果、差異原因、信心等級與可復原狀態；沒有差異時也要明確說明。

### 2. Route Conflict Sentinel：區網與隧道路由衝突哨兵

專門處理 Tailscale、WireGuard、企業 VPN、遊戲加速器與跳板最常見但一般工具說不清楚的問題。

- 比較 VPN 啟用前後的預設路由、私有網段路由、底層閘道及 DNS。
- 偵測「外網可用但 NAS／路由器失聯」、「私有網段被隧道路由覆蓋」、「VPN slot 被占用」等模式。
- 不宣稱知道其他 App 的內部規則；結論以可觀察證據與可信度呈現。
- 提供針對情境的下一步：關閉接受子網路路由、允許 LAN、停用加速器後對照，或改走系統 Private DNS。實際設定名稱依供應商不同，因此以引導而非自動修改為主。

驗收條件：至少涵蓋外網正常／LAN 失聯、預設路由改變、DNS VPN slot 衝突三種可重現案例。

### 3. Resolver Truth Lab：不先改設定的 DNS 真相對照

目前 DNS 切換能改變行為，但尚不能先回答「到底是哪個 resolver 出問題」。

- 同時比較系統解析與使用者選定的 Cloudflare、Google、Quad9 回覆、延遲及錯誤類型。
- 將 socket 綁定到指定 Android `Network`，避免 Wi-Fi、行動網路與 VPN 結果混在一起。
- 顯示 Private DNS 主機名稱（平台可見時）、分流 DNS／split DNS 跡象、NXDOMAIN 差異與 IPv4/IPv6 回覆差異。
- 這是診斷，不會默默切換 DNS；確認問題後才提供直接套用與前後驗證。

驗收條件：可區分系統 resolver 失敗、指定 resolver 皆失敗、只有單一 resolver 回覆不同，以及外部 VPN 攔截／覆寫結果等狀態。

### 4. Path A/B：同一支手機比較兩條網路

回答「是 Wi-Fi 壞了，還是服務本身壞了」。

- 以 `Network.openConnection`、network-bound socket 分別對 Wi-Fi、行動網路及可觀察的 VPN 路徑執行相同低流量 probe。
- 不改全機預設路由；啟用行動數據測試前顯示預估流量並取得明確同意。
- 結果用並排差異呈現：DNS、TLS/HTTPS、延遲、IPv4/IPv6、服務可達性。
- 雙卡或多個 validated network 不猜測，要求使用者選擇可辨識的路徑。

驗收條件：至少在 Wi-Fi + 行動網路同時可用時完成相同測項的獨立連線，且測試封包不外洩到另一條 Network。

### 5. Event Timeline：事件驅動、低打擾的網路時間線

固定每分鐘打一次網路只能告訴使用者「某分鐘失敗」，不一定知道原因。

- 先記錄低成本的系統事件：網路取得／遺失、capability 改變、VPN 出現、IP/DNS/route 改變、飛航模式與 captive portal。
- 只有發生有意義變化或第一次失敗時才執行外部 probe；正常時不持續製造流量。
- 使用者可在事件上加註「開始打遊戲」、「開啟 Surfshark」、「公司 VPN 上線」等本機標記。
- 將相鄰事件合併成人話，例如「21:40 VPN 離線；12 秒後底層 Wi-Fi 驗證恢復，Fastly 延遲下降 84 ms」。

驗收條件：待機期間沒有固定外部輪詢；狀態變化可觸發一次有界檢查；通知只在狀態轉換或持續異常時出現。

### 6. Local Explanation Engine：有證據的人話結論

- 使用本機規則圖，不依賴雲端 LLM，也不把網路紀錄上傳。
- 每項結論分成「觀察」、「推論」、「建議」，避免把猜測寫成事實。
- 顯示信心：高（直接 API／probe 證據）、中（多項一致跡象）、低（平台資訊不足）。
- 首批情境：DNS 失敗但 HTTPS IP 可達、外網正常但 LAN 失聯、VPN 前後路徑改變、captive portal、IPv6 可用但 IPv4 異常、特定 CDN 服務異常。

驗收條件：每條建議都能追溯到具名證據；沒有足夠證據時輸出「目前無法判定」而非通用話術。

### 7. Evidence Capsule：可分享、可刪減的診斷膠囊

- 產生結構化 JSON 與易讀文字，後續可加 HTML/PDF；內容包含 before/after、裝置與 Android 版本、測試端點版本、時間線與證據。
- 匯出前逐項勾選是否包含公開 IP、本機 IP、SSID、VPN 候選與時間資訊。
- 預設遮蔽可識別資訊，附 schema 版本與檔案雜湊，方便客服核對而不需要本 App 後端。
- 可由另一台裝置或桌面檢視器讀取，但不自動上傳。

驗收條件：預設匯出不含完整 IP／SSID；使用者可預覽實際內容；舊版膠囊可依 schema 版本讀取。

## 未來網路環境的準備

以下不是首頁堆按鈕，而是納入快照與解釋引擎的能力：

- IPv6-first、IPv6-only、NAT64/DNS64、464XLAT 與 CGNAT 跡象。
- HTTP/3／QUIC 可達性、UDP 被阻擋後回退 HTTP/2 的情況。
- 系統 Private DNS 是否啟用，以及平台可觀察範圍內的 DoT 生效證據。
- Ethernet、USB tethering、Bluetooth PAN、衛星或高延遲鏈路以 transport + 性質描述，不用脆弱的品牌猜測。
- 服務診斷套件：GitHub/Fastly、遊戲登入、語音通話、影音串流、NAS／遠端存取。每套件必須公開端點、流量上限與判定規則。

## 產品資訊架構

首頁不應成為工具格子。建議改為三層：

1. **現在**：一句目前狀態、主要證據、最值得做的一個動作。
2. **比較**：建立基準、執行變更、查看前後差異。
3. **紀錄**：事件時間線、診斷膠囊與進階工具。

DNS、Fastly、Path A/B 等是診斷能力，從情境流程進入；進階使用者仍可由「工具」頁直接開啟。

## 分期計畫

### Phase 1 — 能證明變更有效

- 統一 `DiagnosticSnapshot` 資料模型與 Room schema。
- Change Lab MVP：手動建立 before/after、DNS 變更自動驗證、差異卡。
- DNS-only VPN 啟動後的實際解析驗證與失敗回復。
- Evidence Capsule v1（文字 + JSON、預覽與遮蔽）。

### Phase 2 — 能指出隧道與路由衝突

- Route Conflict Sentinel。
- Event Timeline 改用 `NetworkCallback` 事件驅動。
- 外部 VPN／加速器關閉前後引導與對照。
- Local Explanation Engine 首批規則與可追溯證據。

### Phase 3 — 能比較兩條路徑

- Resolver Truth Lab。
- Wi-Fi／行動網路 Path A/B。
- IPv4／IPv6、NAT64／CGNAT 狀態模型。
- 情境入口：外網失效、LAN/NAS 失聯、遊戲不穩、GitHub 慢。

### Phase 4 — 面向下一代協定

- HTTP/3／QUIC 與回退診斷。
- 可版本化的服務診斷套件。
- 選配桌面膠囊檢視器；維持無帳號、無遙測後端的預設。

## 不做與停損條件

- 不用不透明「網路健康分數」取代證據。
- 不掃描整個 LAN、不抓取其他 App 流量、不要求 Accessibility 來猜使用中的 App。
- 不為了辨識 VPN 品牌建立永遠追不完的套件名稱資料庫。
- 不在沒有流量預估、冷卻與同意的情況下加入大型測速。
- 若 Android API 無法可靠支持某項判定，降級為觀察值或移除，不以文案掩蓋技術限制。

## 成功指標

- 使用者從發現問題到得到第一個可行動結論的中位時間。
- 完成一次 before/after 驗證的比例。
- 結論中具有可追溯證據的比例（目標 100%）。
- 正常狀態下每小時外部請求數與資料量。
- 診斷膠囊在不包含敏感欄位時仍足以重現判定的比例。
- 實機矩陣中「無法判定」是否誠實一致，而非不同廠牌產生錯誤結論。
